# Sorna Oracle Specification

Status: Draft design specification

This document defines what Sorna means by an **oracle**, how an oracle is
constructed from a contract, what it may observe, and what evidence it must
produce.

The central requirement is independence: an oracle must evaluate an
implementation against an explicit contract without deriving its expectations
from the implementation under test.

## 1. Definition

An oracle is a constrained, executable interpretation of a sealed contract.
It receives a contract, generates or selects observations to make, evaluates
the system's externally visible behavior, and returns a verdict with evidence.

Conceptually:

```text
oracle(contract, public_interface, fixtures, observation)
  -> expectation_result + evidence
```

The oracle may contain examples, properties, state models, generators, and
metamorphic relations. It is not required to be generated by an LLM, and it is
not synonymous with a test file. A test is one execution of an oracle rule;
the oracle is the rule and its decision procedure.

An oracle may answer questions such as:

- Did this request receive the required status and response shape?
- Was invalid input rejected according to the contract?
- Did a state transition preserve the required invariant?
- Did two related inputs produce responses with the required relationship?
- Did a deliberately changed implementation behavior become observable as a
  contract violation?

An oracle must not answer by inspecting source code, private state, internal
call graphs, implementation-specific snapshots, or a test suite derived from
the implementation.

## 2. Contract, oracle, test, and mutation

These concepts must remain separate:

| Artifact | Purpose | May depend on implementation? |
| --- | --- | --- |
| Contract | States the behavior that is required, allowed, or intentionally unspecified | No |
| Oracle | Interprets the contract and decides whether an observation satisfies it | No |
| Test case | Supplies an input sequence and executes oracle rules | No during generation |
| System under test | Produces the observations being evaluated | It is the implementation |
| Mutation | Deliberately changes behavior to challenge the oracle | Derived from the test target or contract policy |
| Evidence record | Makes the run reproducible and auditable | Records provenance, not private implementation semantics |

The desired direction is:

```text
sealed contract -> oracle -> frozen tests -> black-box observation -> verdict
```

The prohibited direction is:

```text
implementation -> inferred expectations -> passing tests
```

## 3. Contract input model

The first Sorna contract format should be machine-readable but remain easy for
a human to review. Every normative rule needs a stable identifier so that
results can point back to the exact requirement.

Illustrative shape:

```yaml
contract:
  id: todo-api
  version: 1
  status: sealed
  interface:
    protocol: http-json
    base_path: /api
    entrypoint: http://sut.invalid

  rules:
    - id: create.valid.status
      strength: must
      subject: POST /todos
      requirement: A valid todo is accepted.
      expect:
        status: 201

    - id: create.valid.response
      strength: must
      subject: POST /todos
      expect:
        body:
          type: object
          required: [id, title, completed]
          properties:
            id: { type: string, non_empty: true }
            title: { type: string, non_empty: true }
            completed: { type: boolean, equals: false }

    - id: create.invalid.empty-title
      strength: must
      subject: POST /todos
      given:
        body: { title: "" }
      expect:
        status: 400

    - id: list.includes-created-item
      strength: must
      subject: GET /todos
      invariant: An item accepted by create is observable in a subsequent list.

  unspecified:
    - response.body.created_at format
    - ordering of unrelated todos
```

The format needs at least these concepts:

- `id`: stable rule identifier.
- `strength`: whether the rule is mandatory, permitted, advisory, or
  explicitly unspecified.
- `subject`: public operation, UI flow, or observable boundary.
- `given`: preconditions, fixtures, and state setup.
- `when`: input or action sequence.
- `expect`: observable requirements.
- `invariant`: a rule that must hold across observations or state transitions.
- `unspecified`: behavior the oracle must not accidentally turn into a
  requirement.

The contract is sealed before oracle generation. Changes after sealing create
a new contract version and a new run lineage; they do not silently rewrite a
previous oracle result.

## 4. Oracle structure

A Sorna oracle is composed of six explicit parts:

### 4.1 Input model

Defines concrete examples, boundary values, invalid values, generated values,
and action sequences. Inputs must come from the contract, public fixtures, or a
deterministic generator configuration.

The input model should make boundary intent visible. For example, if a title
must be non-empty, the oracle should normally include at least:

- the shortest valid title;
- a typical valid title;
- the empty string;
- whitespace-only input if whitespace semantics are relevant;
- a value at the documented maximum;
- a value beyond the documented maximum.

### 4.2 Observation adapter

Converts a public interaction into a normalized observation. Adapters may
support HTTP, a command-line interface, a browser boundary, or another
explicitly supported protocol.

An observation should include only externally visible information, such as:

```json
{
  "status": 201,
  "headers": {"content-type": "application/json"},
  "body": {"id": "t-1", "title": "Read spec", "completed": false},
  "events": []
}
```

Adapters may normalize volatile values such as timestamps or generated IDs,
but every normalization rule must be declared and recorded. Normalization must
not erase the behavior that the contract is intended to verify.

### 4.3 Expectation rules

Expectation rules compare an observation with the contract. They should prefer
semantic predicates over complete snapshots:

- exact status where status is normative;
- required fields and types;
- allowed value sets or ranges;
- relationships between fields;
- required error categories;
- state-transition invariants;
- explicitly permitted variation.

An expectation must be traceable to one or more contract rule IDs.

### 4.4 State model

Some behavior can only be evaluated as a sequence. A state model describes
publicly observable transitions without depending on private implementation
state.

```text
empty --create(valid)--> contains(todo)
contains(todo) --complete(todo)--> contains(completed todo)
contains(todo) --delete(todo)--> empty
```

The oracle may assert that a transition is allowed, forbidden, idempotent, or
reversible when the contract says so. It must not assume extra transitions just
because the implementation happens to support them.

### 4.5 Properties and generators

Properties express rules across many inputs. Generators produce inputs from
contract-defined domains rather than reverse-engineering types from source.

Examples:

- Every accepted title remains a string after a round trip.
- Repeating an idempotent operation does not change the observable result.
- A rejected invalid request does not create a visible item.
- Pagination never returns more than the documented page size.

Generators must be seeded, versioned, and replayable. A failing generated case
must be saved as a concrete fixture.

### 4.6 Metamorphic relations

When an exact expected output is difficult to state, the oracle may compare
related executions whose relationship is specified by the contract.

Examples:

- Adding an unrelated field to an accepted request does not change the
  required result.
- Repeating a read operation produces an equivalent observation.
- Reordering independent inputs does not alter the resulting set.

Metamorphic relations are valid only when the contract explicitly establishes
the relationship. They must not be inferred from observed implementation
behavior.

## 5. Oracle authoring modes

Sorna should support these modes, in increasing order of complexity:

1. **Example oracle** — fixed inputs and explicit expectations.
2. **Boundary oracle** — contract-derived limits and invalid cases.
3. **Property oracle** — predicates over generated observations.
4. **Stateful oracle** — action sequences and public state transitions.
5. **Metamorphic oracle** — relationships between multiple executions.
6. **Differential oracle** — comparison with another independently specified
   implementation or reference model, only when that reference is itself
   governed by an explicit contract.

The first implementation should focus on example, boundary, and property
oracles. Stateful and metamorphic support should be designed into the result
model but can follow after the first vertical slice.

## 6. Independence and information barriers

The oracle-generation environment may receive:

- the sealed contract;
- public interface documentation;
- public fixtures explicitly attached to the contract;
- generic Sorna runner documentation;
- deterministic generation libraries;
- its own generated files and logs.

It must not receive:

- the implementation checkout or source archive;
- private implementation documentation;
- generated schemas or snapshots obtained from the implementation;
- implementation-specific test helpers;
- another agent's implementation transcript;
- failing implementation results during test generation;
- coverage reports or mutation results before the oracle is frozen.

The strongest practical boundary is capability-based: the oracle process gets a
separate workspace containing only permitted inputs and a narrow runner
interface. Tool-call logs and filesystem audit records are useful supporting
evidence, but a transcript alone is not a security guarantee.

Sorna should record the boundary as part of the run:

```yaml
information_barrier:
  allowed_roots:
    - /run/input/contract
    - /run/input/public-fixtures
    - /run/output/oracle
  denied_roots:
    - /run/implementation
  network: disabled
  generation_completed_before_sut_access: true
```

If the boundary cannot be established, the run must be labeled
`independence-unverified` rather than presented as a proven independent
oracle.

## 7. Freeze protocol

Oracle generation is a pre-execution phase:

1. Resolve and hash the sealed contract.
2. Create the isolated oracle workspace.
3. Generate or author oracle rules and concrete test cases.
4. Run syntax and self-consistency checks without accessing the SUT.
5. Review the generated oracle, if human review is required.
6. Freeze and hash the oracle artifact and generated cases.
7. Grant the runner access to the SUT.
8. Execute the frozen cases.

After step 6, an oracle may not adapt its expectations based on failures. A
mechanical repair to a runner or serialization problem must create a new oracle
revision and be recorded as such.

## 8. Verdict model

At the individual rule level, Sorna should distinguish:

- `pass`: the observation satisfies the rule;
- `fail`: the observation violates the rule;
- `error`: the oracle or adapter could not evaluate the rule;
- `timeout`: execution exceeded the configured limit;
- `inconclusive`: the contract does not provide enough information;
- `skipped`: the rule was intentionally excluded with a recorded reason.

At the run level, Sorna should report both rule results and contract coverage.
Coverage means which contract rules were exercised; it is not line coverage.

The oracle must not silently convert `inconclusive` into `pass`. This is how
underspecified behavior remains visible instead of becoming a false guarantee.

## 9. Mutation interaction

Mutation testing challenges the sensitivity of a frozen oracle. It does not
prove that the contract is complete or correct.

Sorna should support two mutation planes:

### Implementation mutations

Deliberately alter externally observable behavior, for example:

- change a required status code;
- remove a required response field;
- accept an invalid boundary value;
- skip persistence;
- return stale frontend state;
- alter an error category.

Expected result: the relevant oracle rule should fail, producing a `killed`
mutation.

### Contract mutations

Deliberately weaken or change a contract rule, for example:

- remove a required field;
- widen an allowed range;
- change a required status;
- remove an invalid-input case;
- weaken a state invariant.

Expected result: the oracle suite or review process should make the change
visible. A contract mutation is not necessarily executable against the SUT;
Sorna must label the mutation plane explicitly.

Mutation outcomes should include:

- `killed`;
- `survived`;
- `equivalent`;
- `invalid`;
- `timeout`;
- `inconclusive`.

Surviving mutations are findings for investigation, not automatic proof that
the implementation is wrong. A mutation score is a sensitivity signal.

## 10. Evidence record

Every oracle run should produce a machine-readable manifest containing at least:

```json
{
  "run_id": "sorna-2026-0001",
  "contract": {
    "id": "todo-api",
    "version": 1,
    "sha256": "..."
  },
  "oracle": {
    "artifact_sha256": "...",
    "case_count": 18,
    "generator_seed": 4242
  },
  "boundary": {
    "policy_sha256": "...",
    "independence": "verified"
  },
  "sut": {
    "revision": "...",
    "adapter": "http-json-v1"
  },
  "results": {
    "passed": 15,
    "failed": 3,
    "inconclusive": 0
  },
  "mutations": {
    "killed": 8,
    "survived": 1,
    "equivalent": 1
  }
}
```

The evidence bundle should also include:

- contract and oracle hashes;
- public inputs and generated seeds;
- normalized observations;
- rule-level verdicts and explanations;
- implementation revision or image digest;
- runner and environment versions;
- mutation catalogue and outcomes;
- allowed/denied roots and sandbox policy;
- tool and filesystem events where available;
- human approvals, amendments, and waivers.

Tool-call evidence strengthens an audit trail, but the structural access policy
is the primary independence control.

## 11. First vertical slice

The first Sorna implementation should target one HTTP/JSON boundary and
support:

- a sealed YAML or JSON contract;
- fixed example cases;
- required status and JSON field assertions;
- type, range, enum, and presence predicates;
- deterministic boundary cases;
- a small property hook;
- normalized observations;
- frozen oracle and contract hashes;
- JSONL rule results;
- one or two implementation mutation operators;
- a reproducible evidence manifest.

It should not begin with a full browser automation system, arbitrary language
support, adaptive test generation, or a claim of cryptographic proof.

## 12. Design principles

1. The contract is the authority, not the implementation.
2. The oracle is a decision procedure, not a screenshot collection.
3. Unspecified behavior stays unspecified.
4. Expectations freeze before implementation results are visible.
5. Every verdict points to a contract rule and an observation.
6. Mutation testing measures sensitivity, not truth.
7. Isolation must be structural; logs alone are not enough.
8. An inconclusive result is better than an invented guarantee.
9. Every change creates a traceable artifact revision.
10. Sorna can run independently; Herdr Sentinel may orchestrate it but must not
    redefine its semantics.

## 13. Open decisions

- Which contract syntax should be canonical for the first release?
- Should oracle rules be compiled to a Sorna IR before execution?
- Which expression language is safe and portable for predicates?
- How should browser observations be normalized without overfitting to a UI?
- Which sandbox mechanism will provide the initial information barrier?
- Which mutation operators are deterministic and meaningful for the first
  HTTP/JSON adapter?
- What level of human review is required before an oracle can be sealed?

## 14. Current first implementation slice

The first executable slice uses a canonical `ingen.oracle/v1` JSON artifact:

- `status: frozen`;
- the sealed contract ID, version, and SHA-256 hash;
- the sealed policy SHA-256 hash;
- one materialized case for each contract rule.

The executable loader additionally requires at least one case and rejects
duplicate case IDs, duplicate rule IDs, and unsupported contract strengths.
These are artifact-integrity checks; they do not establish that the contract or
oracle is correct.

The `sorna oracle freeze` command seals the identities, prepares a host
enforcement profile, starts a separate child process, and verifies the
child-written oracle before producing evidence:

```text
draft contract + draft policy
          |
          v
parent seals identities and prepares the host policy
          |
          v
sandboxed child reads contract -> materializes cases -> writes oracle.json
          |
          v
parent verifies hashes -> writes manifest/events/checksums
```

The child process exists to make the access boundary operational. An
in-process generator call would produce a useful artifact but would not prove
that the oracle writer was subject to the host policy. The current bundle
records process preparation, start, completion, resolved capability roots, and
policy bytes. On macOS it also records scoped Seatbelt access decisions in
`events/access.jsonl` and reports whether that telemetry was captured with
gaps. The HTTP runner consumes the canonical frozen artifact and records its
oracle hash in subject-run evidence; subject-process isolation and assurance
promotion remain subsequent slices.
