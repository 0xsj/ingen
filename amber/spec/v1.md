# Amber core specification v1

This document defines the first language-neutral Amber contract. The key words
MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are normative.

## 1. Purpose and scope

Amber records the provenance of application-level work:

- the logical work being performed;
- the concrete execution that performed it;
- the relationship to a parent or cause;
- the actor and tenant attribution; and
- whether the execution is a retry or replay.

Amber is not a distributed tracing protocol and is not an authorization
mechanism. A host MAY copy Amber fields into logs, traces, messages, or storage,
but those integrations are outside this core contract.

## 2. Core value

An Amber `Provenance` value has the following fields:

| Field | Type | Required | Meaning |
| --- | --- | --- | --- |
| `version` | positive integer | yes | Wire-contract version. For this document, `1`. |
| `work_id` | ID | yes | Stable identity of one logical unit of work. |
| `execution_id` | ID | yes | Identity of this concrete execution. |
| `correlation_id` | ID | yes | Stable identity used to group related work across a flow. |
| `causation` | Causation | no | The immediate known cause of this execution. |
| `origin` | Origin | yes | How this execution entered the application. |
| `depth` | non-negative integer | yes | Number of derived execution transitions from the flow root. |
| `attempt` | positive integer | yes | Attempt number for this `work_id`; starts at `1`. |
| `attribution` | Attribution | no | Actor and tenant information. |
| `mode` | Mode | yes | Normal execution, retry, or replay. |
| `references` | array of Reference | no | Additional bounded relationships to typed external values. |

Implementations MUST treat unknown object fields as forward-compatible data and
MUST preserve them when they support lossless decode/encode. They MUST reject
unknown enum values unless an explicit forward-compatibility mode is provided.

### 2.1 IDs

An `ID` is a lowercase canonical UUID string (`xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx`)
using hexadecimal characters, where the UUID version and variant bits are
valid. Implementations MUST generate a fresh `execution_id` for every execution
and a fresh `work_id` for every new logical unit of work.

IDs are opaque to consumers. They MUST NOT be interpreted as timestamps,
sequences, or authorization credentials.

### 2.2 Origin

`origin` MUST be one of:

- `local` — created by local application code without a trusted incoming Amber value;
- `incoming` — derived from a value received from another application or process;
- `retry` — created by retrying a prior execution; or
- `replay` — created by intentionally re-running a prior execution.

`retry` and `replay` origins are descriptive. The corresponding `mode` fields
carry the source execution relationship.

### 2.3 Mode

`mode` MUST be exactly one of:

```json
{ "kind": "normal" }
```

```json
{
  "kind": "retry",
  "of_execution_id": "2f8f5f3a-9d48-4c21-9b4f-1c4d2f4fbf4d"
}
```

```json
{
  "kind": "replay",
  "of_execution_id": "2f8f5f3a-9d48-4c21-9b4f-1c4d2f4fbf4d",
  "replay_id": "7b5c3cb8-74af-4b2d-8e77-9a8be8f35a62"
}
```

For `normal`, no additional fields are allowed. For `retry`,
`of_execution_id` MUST identify the execution being retried. For `replay`, both
`of_execution_id` and a fresh `replay_id` are required. A replay retains the
same `work_id` as the source execution and receives a new `execution_id`.

## 3. Causation and attribution

### 3.1 Causation

`Causation` identifies the immediate known cause:

```json
{
  "kind": "execution",
  "id": "2f8f5f3a-9d48-4c21-9b4f-1c4d2f4fbf4d"
}
```

The `kind` MUST be one of `execution`, `event`, `message`, `request`, or
`artifact`. The `id` MUST be a valid ID. An implementation MAY add a bounded
`type` string to distinguish domain-specific values:

```json
{
  "kind": "event",
  "id": "2f8f5f3a-9d48-4c21-9b4f-1c4d2f4fbf4d",
  "type": "invoice.paid"
}
```

`causation` is the immediate cause, not a complete ancestry list. Consumers
that need ancestry SHOULD follow stored links outside the core value.

### 3.2 Attribution

`Attribution` MAY contain:

```json
{
  "initiated_by": { "id": "...", "type": "user" },
  "executed_by": { "id": "...", "type": "service" },
  "on_behalf_of": { "id": "...", "type": "organization" },
  "tenant_id": "..."
}
```

Each actor object MUST contain a non-empty `id` and `type`. Each attribution
field is optional, including `tenant_id`; when present, `tenant_id` is an
application-defined non-empty string. Actor identifiers are application-defined
strings and are not required to be UUIDs. Amber records attribution only; it
does not validate that an actor is allowed to act for another actor or tenant.

## 4. References

`references` is an optional list of typed relationships:

```json
{
  "type": "customer",
  "id": "customer-123",
  "relation": "related"
}
```

The `type` and `id` fields are required non-empty strings. `relation` is an
optional non-empty string. Reference values MUST be bounded by the host
implementation. The default maximum is 32 references per value, and the
default maximum length is 256 Unicode scalar values per string. Implementations
MAY configure lower limits but MUST NOT silently create unbounded collections.

The reference list is descriptive and does not imply ownership, authority, or
existence of the referenced value.

## 5. Invariants

Every valid value MUST satisfy all of the following:

1. `version` is `1`.
2. All IDs are valid canonical UUIDs.
3. `work_id`, `execution_id`, and `correlation_id` are present.
4. `depth` is at least `0`.
5. `attempt` is at least `1`.
6. `execution_id` is unique for each created execution within the caller's ID domain.
7. `mode` and `origin` agree: `retry` uses retry mode/origin, `replay` uses replay mode/origin, and normal local/incoming values use normal mode.
8. A retry or replay has a source execution ID different from its own execution ID.
9. A derived execution has `depth` exactly one greater than its parent when a parent is supplied.
10. No transition mutates the input value.
11. Incoming values are data to inspect and validate; decoding one MUST NOT implicitly install it as process-global or request-global context.

## 6. Valid transitions

Transitions create new immutable values. They MUST preserve `work_id` and
`correlation_id` unless the transition explicitly starts a new logical flow.

### 6.1 Start new work

`Start` creates a value with:

- fresh `work_id`, `execution_id`, and `correlation_id`;
- `origin: "local"`;
- `mode: {"kind": "normal"}`;
- `depth: 0`; and
- `attempt: 1`.

### 6.2 Derive child work

`Child(parent, cause?)` creates a new execution for a new logical child unit:

- fresh `work_id` and `execution_id`;
- inherited `correlation_id`;
- `causation` set to the supplied cause, or to the parent's `execution_id` as an execution cause;
- inherited attribution unless overridden by an explicit child attribution;
- `origin: "local"` for local derivation or `"incoming"` when created from an incoming boundary;
- `mode: {"kind": "normal"}`;
- `depth: parent.depth + 1`; and
- `attempt: 1`.

### 6.3 Retry an execution

`Retry(previous)` creates another execution of the same logical work:

- same `work_id` and `correlation_id`;
- fresh `execution_id`;
- `causation` set to the previous execution;
- `origin: "retry"`;
- `mode.kind: "retry"` and `mode.of_execution_id` set to the previous execution;
- same `depth`; and
- `attempt: previous.attempt + 1`.

### 6.4 Replay an execution

`Replay(previous)` creates an intentional re-execution:

- same `work_id` and `correlation_id`;
- fresh `execution_id` and `replay_id`;
- `causation` set to the previous execution;
- `origin: "replay"`;
- `mode.kind: "replay"` and `mode.of_execution_id` set to the previous execution;
- same `depth`; and
- `attempt` equal to the previous attempt (replay is not a retry).

### 6.5 Incoming context

At an incoming boundary, an adapter MUST:

1. inspect and decode the external value;
2. validate it against this specification;
3. either accept it as the current context or create a new child context according to adapter policy; and
4. restore the previous context when the boundary ends.

Invalid, oversized, or unsupported incoming values MUST be rejected or treated
as absent according to adapter policy. They MUST NOT cause a process-wide
failure by default, and they MUST NOT overwrite an unrelated context silently.

### 6.6 Incoming inspection policy

Core implementations MUST expose an explicit incoming inspection policy with
these modes:

- `reject` — return an error for malformed, unsupported, or oversized input;
- `ignore` — treat malformed, unsupported, or oversized input as absent.

An absent incoming value is an omitted value or a zero-length input. Whitespace
or other non-empty malformed input is invalid, not absent. Incoming JSON MUST
be limited to at most 16,384 UTF-8 bytes before decoding. Implementations MAY
configure a lower limit but MUST NOT accept an unbounded incoming value.

Inspection MUST return either one validated `Provenance` value or an absent
result. Installing an accepted value into a context MUST be a separate,
explicit operation. When inspection returns absent, context installation MUST
return the original context unchanged.

### 6.7 Trust validation

Structural validity does not establish authenticity, sender identity, or
authorization. Amber v1 transport values are unsigned by default. An
implementation MAY accept an application-provided incoming validator after
structural decoding and before context installation.

The validator MUST run only for a present, structurally valid value. A
validator failure MUST either be returned as an incoming error under `reject`
or treated as absent under `ignore`; the value MUST NOT be installed when the
validator fails. A validator or accepted Amber value MUST NOT by itself grant
authorization.

Signature formats, key distribution, rotation, replay protection, and
transport-specific authenticated envelopes are outside this v1 core contract.
An authenticated extension MUST define those properties explicitly instead of
being inferred from a valid unsigned Amber value.

## 7. JSON wire contract

The canonical JSON representation uses the field names below. JSON objects MAY
contain unknown fields for forward compatibility, but known fields MUST retain
the types defined here.

```json
{
  "version": 1,
  "work_id": "0f7d2b1f-0d5f-4a16-89e9-46a10b9dd4b5",
  "execution_id": "2f8f5f3a-9d48-4c21-9b4f-1c4d2f4fbf4d",
  "correlation_id": "4c5a0cb3-750c-4f65-ae72-c2bf9e0f8d87",
  "causation": {
    "kind": "event",
    "id": "c6f5f7cc-5b26-4cc8-86d0-5c9c2b4d629d",
    "type": "invoice.paid"
  },
  "origin": "incoming",
  "depth": 2,
  "attempt": 1,
  "attribution": {
    "initiated_by": { "id": "user-42", "type": "user" },
    "executed_by": { "id": "billing-worker", "type": "service" },
    "tenant_id": "tenant-7"
  },
  "mode": { "kind": "normal" },
  "references": [
    { "type": "invoice", "id": "invoice-123", "relation": "subject" }
  ]
}
```

Serialization MUST be deterministic for equivalent values: implementations
MUST emit the same field names and enum spellings, and SHOULD emit object keys
in the order shown above. JSON whitespace is insignificant.

## 8. Context safety

Context APIs SHOULD expose paired install/restore operations or an equivalent
scoped mechanism. A caller that installs an Amber value MUST be able to restore
the exact prior value, including an absent value. Context propagation MUST be
explicit at concurrency and process boundaries; implementations MUST NOT infer
context from mutable global state when a caller supplies an explicit value.

Adapters MAY redact or omit attribution and references when crossing a trust
boundary, but MUST document that policy and MUST validate the resulting value.

## 9. Compatibility and conformance

Implementations MUST provide behavior equivalent to the transitions in section
6 and MUST reject malformed values described in section 5. Conformance fixtures
will exercise valid values, invalid values, retry/replay behavior, and context
restoration. Fixtures should compare semantic values rather than JSON
whitespace or object-key order.
